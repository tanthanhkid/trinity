# Changelog

All notable changes to Trinity are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## Unreleased

### Added
- **Channel abuse protection for hosted companies** (`MULTI_TENANT=true`; single-company installs are unaffected): all companies share one Meta (and Zalo/Google) app, so one company spamming could get the whole app restricted. Each plan now carries limits counted on the server per company — bulk messages per day (Messenger broadcasts + Zalo ZNS), recipients per campaign, posts/scheduled posts per day (per target channel), automatic comment replies per hour (`PLANS[..].channelLimits`; the `custom` plan is wide but capped). Over the limit the action is refused with a clear message and logged. Graph API errors are tracked per company (#368 policy/spam, #551, #17, #32 on outgoing calls; app-wide limits #4/#613/429 back off all companies instead): past the threshold the company's bulk and automatic Facebook/Instagram sending pauses for a few hours — work is held and resumes afterwards, never cancelled — an event is recorded and a warning shows in the app for every user. The platform owner can lock a company's outbound channels with `pnpm --filter @trinity/prisma channel:lock -- lock <companyId> [reason]` (inbound keeps working; `unlock`, `resume`, `list` too). `GET /settings/channel-guard`, the new MCP tool `get_channel_limits`, a warning banner and a Settings › Features card show limits, usage, lock and pause state. See `docs/multi-tenant.md`.
- **Start wizard without an AI assistant**: the first sign-in now asks for your type of business (education center, retail and services, clinic/spa/vet, real estate, or Other), then the modules you want (ticked for your type), and builds the system with one press. 2–3 clearly fake sample records are added and delete themselves when the first real customer or custom record is created (UI, API or AI). `POST /setup/build` and the MCP tool `setup_build` do the same build; industry presets live in `@trinity/rbac` (`INDUSTRY_PRESETS`).
- **Connect your assistant in one paste** (#6): step 1 of onboarding asks which assistant you use (ChatGPT, Claude, Claude Code, Antigravity, Gemini CLI, Cursor, Codex CLI, VS Code Copilot, other) and copies one prompt with the server address, OAuth-only login, the exact way to add the server for that client (or `mcp-remote` as a fallback), a short `trinity` rule or skill for the client, and the first step. `GET /setup/connect-prompt`; `get_setup_guide` accepts `agent` and returns `connect_prompt`.
- **AI-native overview** (#4): the home page opens with "AI assistants at work" (which assistants are connected, who is active now, what the AI did today) and "Connected channels" (Fanpage, Zalo OA, posting channels, payments, online store, sales connectors) with status and today's counts. With no assistant connected, it shows a step-by-step invite. New `GET /reports/dashboard-channels`, filtered by enabled features and the viewer's permissions.
- **Feature switches** (#4): Settings › Features shows grouped cards (core, channels & inbox, sales, people, advanced) with one switch each; the menu and the related Settings sections only show what is on. New `inbox` switch for the Inbox menu. A newly built workspace always turns on the core set (overview, customers, tasks, reports, inbox, AI connections) plus what the AI picks for the industry.
- **AI assistant (MCP)**: `list_features`, `set_features` (switching off needs `confirmed_by_user`), `save_crm_option` (add, rename, reorder or hide customer sources, stages and statuses; no delete), `get_connected_channels`.
- **Invite staff by link** (hosted, multi-company mode): the owner of a company (anyone with `users.manage`) adds staff to their own company. Settings › Users › "Mời bằng link" takes an email and a role and gives a one-time link (7 days, bound to the company) to copy and send by Zalo or Messenger; Trinity sends no email. Pending invitations can be cancelled or re-created (a new link replaces the old one). The public page `/invite/<token>` asks for a name and password, creates the user in the right company with the chosen role and signs them in. Invitations count against the plan's `maxUsers` ("Gói hiện tại tối đa N người, liên hệ để nâng gói."; plan `custom` is unlimited); an email that already belongs to another company is refused with a clear message. The owner can also reset a staff password with a generated temporary password shown once. New API `POST/GET /auth/invitations`, `POST /auth/invitations/:id/revoke`, public `POST /auth/invitations/preview` and `/accept`; MCP tools `create_invitation` (returns the link), `list_invitations` and `cancel_invitation` (no delete tool, no Quản trị role through AI, no password tool). List and cancel follow the `users.manage` scope.
- New hosted companies start on a new plan "Mặc định" (`mac_dinh`, `DEFAULT_SIGNUP_PLAN` in `@trinity/rbac`): every plan-gated feature (Fanpage, Zalo OA, briefings…) stays available, only users are capped at 10, until pricing is settled. A company other than the first with no plan row counts as that plan everywhere (user limit, features, Settings); company 1 and single-company installs stay on unlimited `custom`. Accepting an invitation takes the company's advisory lock as the first statement of its transaction (same lock order as creating, revoking and re-inviting, so no deadlock) and re-checks everything under it: inviter still active with `users.manage`, the invited role not above the inviter's own permissions, the email still free. An invitation whose inviter lost the permission or was locked, or whose role was deleted, no longer holds a seat and shows as unusable; deleting a role cancels its pending invitations. Staff invited by someone with a narrow `users.manage` scope are placed under that person (`manager_id`) so they can manage them. Creating a user or employee for an email that has a pending invitation cancels that invitation first. Doing so for an email whose pending invitation belongs to someone outside your scope answers 409. Locking or deleting an inviter cancels their pending invitations, and accepting re-checks that the inviter is still active with `users.manage` and runs the same office Wi-Fi and single-session checks as login. Re-inviting an email only replaces invitations inside your own `users.manage` scope (409 otherwise). Every way of adding an active user (create, unlock, employees, accept) now counts active users plus pending invitations under one per-company advisory lock, so two at the limit cannot both pass.

### Security
- One function determines the client IP for the whole backend (#116). Before, IPs were read in seven places in five ways: `CF-Connecting-IP` trusted unconditionally once a flag was on, `X-Real-IP` trusted whenever the peer was loopback or a private network (always true behind Next or a local proxy), and the online store and VNPay took the **first** `X-Forwarded-For` entry, which the client controls. Now no client header is trusted unless `TRUSTED_PROXY` names the proxy in front; the IP passed between Trinity processes is HMAC-signed (`x-trinity-client-ip`, ±60 s, checked when the headers arrive so slow uploads are unaffected; a bad or expired signature gets 400). The web app no longer forwards the browser's `X-Forwarded-For`/`X-Real-IP`/`CF-Connecting-IP`/`Forwarded`/`x-trinity-*` headers to the API. An IP that cannot be trusted (loopback, the container gateway, a private-network peer without a signed header such as the `web` container, or marked untrusted by the web process) is never compared with office IPs: login Wi-Fi and attendance checks let the user through instead of comparing a wrong address, login rate limits switch to per-email, the server logs a configuration error and admins see a warning banner (`GET /settings/client-ip/alerts`, MCP tool `get_client_ip_status`) for 24 hours after the last such request.

### Upgrade notes
- **Action required on upgrade — client IP (`TRUSTED_PROXY`).** The backend now reads the client IP in one place and trusts no client header unless `TRUSTED_PROXY` names the proxy in front (see `docs/deployment.md`, "Client IP"). The default is `none` (the TCP peer). Values: `cidr:127.0.0.1/32` (Caddy/nginx on the same machine), `cloudflare-behind:127.0.0.1/32` (Cloudflare in front of Caddy/nginx), `cloudflare` (Cloudflare straight to the app), `cloudflare-tunnel` (Tunnel with a process manager; API `LISTEN_HOST=127.0.0.1`, web `HOSTNAME=127.0.0.1` — not for Docker Compose yet), `cidr:docker-gateway` (Compose behind a proxy on the host), or `none`. With nginx, also set `proxy_set_header X-Forwarded-For $remote_addr;` and `proxy_set_header X-Real-IP "";` in every `location` that reaches the app. **In this release the web app stops forwarding the browser's IP headers to the API and does not sign the IP yet**, so requests that go through `web` (every normal install: Caddy/nginx → web → API, and Docker Compose) reach the API as "IP cannot be trusted": office-IP checks at login and attendance stop comparing addresses and let users through, admins see a warning banner, OAuth/MCP/store rate limits share one bucket and login limits apply per email. If you rely on office-IP checks, wait for the release in which the web app signs the client IP before upgrading.
- **The API no longer starts with the old flags** `ATTENDANCE_TRUST_CF_IP`, `LOGIN_WIFI_TRUST_CF_IP`, `ATTENDANCE_TRUST_PROXY_HEADERS` or `LOGIN_WIFI_TRUST_PROXY_HEADERS` set to true and no `TRUSTED_PROXY` (process-manager installs; Docker Compose never passed these flags to the container). Their old meaning does not map safely to a new value, so nothing is converted silently: the startup error lists the value for each deployment. Set `TRUSTED_PROXY`, then remove the old flags. An invalid `TRUSTED_PROXY`/`CLOUDFLARE_IP_RANGES`, or `cloudflare-tunnel` with a non-loopback listen address, also stops startup.
- New migration `0019_user_invitations` (one new table, and it drops the old "one user per company" trigger from company schemas). Multi-company installs: `prisma migrate deploy`, then `MULTI_TENANT=true pnpm --filter @trinity/prisma migrate:companies`; boot also reinstalls the sync triggers without the old one (`trinity-sync-v3`).
- No other migrations. Running systems keep their feature switches (missing keys still mean on), so the new `inbox` switch starts on. A system counts as already built when `setup_built` exists, when `setup_status` was written as `da_dung`/`dang_dung` (the earlier AI-built flow), or when the `setup_status` row is missing and it has custom tables or real records (fail-open). Such systems are not locked again, and their users go straight into the app. A fresh database from the init migration is `chua_dung`, so it still goes through the wizard, and a half-finished build (tables but no `setup_built`) can be built again. The start-wizard config now lets *first customer*, *channels* and *first post* be skipped by default (configs saved before this change that only allow *first post* are upgraded once; the config now has a `version`).
- New migration `0020_channel_guard` (additive: tables `channel_usage` and `channel_events`). Hosted installs: run `MULTI_TENANT=true pnpm --filter @trinity/prisma migrate:companies` after `prisma migrate deploy`. Boot also adds three columns to `platform.companies` for the channel lock. Single-company installs get no new limits.

## 0.3.0 — 2026-10-15

### Added

## 0.2.0 — 2026-10-15

First release of the fresh public history.

### Added
- **Multi-channel posting**
  - Drafts: save incomplete posts, reopen them in the composer, and publish them. Publishing is atomic, so the same draft cannot be posted twice and approval binds to the exact version the user reviewed.
  - Weekly posting queue: set time slots, then pick "add to queue" and the post goes to the next free slot. An approved post whose slot is gone moves to the next free slot.
  - Reusable hashtag sets and signatures, including a default signature for new posts.
  - UTM tagging of links per channel (`utm_source` = network, `utm_medium=social`). Tagging happens at publish time, so stored text stays clean, and character limits are checked on the tagged text.
  - Per-channel preview: the exact text, the YouTube title and description, the first comment, where "See more" cuts, and warnings.
  - YouTube options (description, tags, category, made for kids, thumbnail, playlist) and a Facebook first comment.
  - Editing and rescheduling of scheduled posts, and cancelling them (status only, nothing is deleted).
  - Bulk import from CSV (Calendar › Import CSV, and the `import_social_posts` MCP tool): check every row first, then create drafts or scheduled posts. An import never publishes immediately, queue rows get distinct slots, and the import is refused if the data changed since the preview.
- **Facebook Page**: comment rules (test or live mode, hide comments with phone numbers), editing Messenger flows, and editing or cancelling pending broadcasts.
- **Inbox**: read every Messenger and Zalo OA conversation; list and reply to Google reviews (once Google grants API access).
- **AI assistant (MCP)**: tools for everything above. New write tools that publish or message customers need the user's approval (`confirmed_by_user`). See the full tool index in `docs/integrations/mcp.md`.

### Changed
- Vitest 4.1 and Vite 6.4 for the web app's test toolchain.
- Dependency security fixes within the same major versions: `sharp` 0.35.5 and `pnpm` overrides. The unused `xlsx` package was removed.

### Upgrade notes
- New migrations `0012_social_drafts`, `0013_social_queue_slots` and `0014_social_snippets`. They are additive only: new tables plus one nullable or defaulted column. Run `prisma migrate deploy`; `docker compose up -d --build` does this through the `migrate` job.

### Breaking / Upgrade notes

- **New migration `0001_session_revocation_won_at_notification_claim`** (additive only: three nullable columns and one new table, no data is dropped or retyped). Run `prisma migrate deploy` before starting the new API — `docker compose up -d --build` does this for you through the `migrate` job. It adds `users.tokens_valid_after`, `deals.won_at`, `notification_logs.webhook_url`, `notification_logs.claimed_at` and the table `revoked_sessions`.
- **The inbound webhook (`POST /api/v1/hooks/in/:token`) now always answers `200 {"status":"accepted","contact_id":null}`** for a valid request. Before, a new customer returned `201 {"status":"created","contact_id":N}` and an existing phone returned `200` with `duplicate` / `replayed` / `accepted`. The responses are now identical so a sender cannot probe which phone numbers are already customers. Integrations that checked for `201` or read `contact_id` must be updated (see `docs/integrations/webhooks.md`).
- **Demo data is off by default in Docker.** `SEED_DEMO_DATA` now defaults to `false` in `docker-compose.yml`, `.env.example` and `install.sh`. If you want demo data, set `SEED_DEMO_DATA=true` before the first start (`SEED_DEMO_DATA=true ./install.sh` also works). An existing `.env` keeps whatever value it already has.
- **Locking a user no longer rewrites the e-mail.** Accounts locked by earlier versions still carry an address like `deleted_<id>_<timestamp>@removed.invalid`; it is not restored automatically, so edit the e-mail before unlocking such an account. Only permanent deletion still frees the e-mail for reuse.

- The "Deploy with Vercel" button now also asks for `INTEGRATIONS_MCP_ENABLED` and `INTEGRATIONS_SECRET_KEY`, and no longer passes the ineffective `project-name`. The MCP default is unchanged (off). The *Bắt đầu* screen tells an admin which variables to set and to redeploy. The Next.js `middleware.ts` file is now `proxy.ts` (Next 16 naming, same behaviour). The login page no longer shows a placeholder admin address or an HR contact line. README: Neon / region / Neon Auth steps for Vercel; Discussions links replaced with Issues.

Behaviour changes to be aware of when self-hosting:

- Sign-out revokes the refresh token of that session on the server (the web app sends it along with `POST /auth/logout`; the revocation is stored in the database, so it survives restarts and works across instances). Changing a password, resetting it (yourself or by an admin), locking an account, or deleting an employee revokes every refresh token issued before that moment, so unlocking an account does not bring old sessions back. Access tokens stay short-lived (15 minutes) as before.
- Locking a user (`PATCH /users/:id {"status":"locked"}` or `DELETE /users/:id`) keeps the e-mail, so the account can be unlocked and used straight away.
- Deleting an employee (soft delete) now also locks the linked login account. Restoring the employee (re-adding with the same e-mail) does not unlock it — unlock the account separately.
- The briefing and the dashboard revenue chart count won deals by the day they were won (new `deals.won_at`, set when the status changes to `won`); deals won before the upgrade fall back to `updated_at`.
- Attendance requests enforce `monthly_forgot_limit` (forgot check-in/check-out) and `monthly_late_early_limit` (late arrival / early leave) per calendar month of the requested work date; rejected requests do not count and `0` means unlimited. Over the limit the request is refused with a Vietnamese message.
- Scheduled `webhook` notifications keep their `webhook_url` until they are sent, and rows stuck in `processing` for more than 15 minutes (for example after a crash) are put back to `scheduled`, or marked `failed` after three attempts, on the existing 2-minute cycle.

- Docker Compose now publishes the API on `127.0.0.1:${API_PORT:-4000}` only. The web container still reaches it over the compose network; put a reverse proxy in front of the web container (port 3000) and do not expose 4000.
- A refresh token is no longer accepted as a Bearer access token (it returns 401).
- Notification webhooks (`webhook_url`) must be `https://` on port 443/8443 and resolve to a public IP; they time out after 5 s and never follow redirects. The push channel is not wired to FCM yet and now reports `skipped` instead of `sent`.
- A manual personal income tax entered on a payslip now overrides the system-computed tax instead of being deducted on top of it.
- Payslips removed from a period can no longer be approved or edited, and deleted employees are no longer included when payslips are generated.
- Kanban column colours must be hex values (e.g. `#198754`).
- Query strings that carry OAuth or token parameters (`code`, `state`, `token`, ...) are redacted in logs.
- Scheduled notifications are now claimed in batches of 100 (previously all due rows were claimed but only 100 processed).
- MCP/AI output masks dotted or comma-grouped `84…` phone numbers instead of treating them as money.
- Attribute definitions of type `select`/`multiselect` must have at least one option (400 otherwise). Salary rules return 400 (not 500) for invalid formulas or non-numeric `amount`; salary components accept `is_taxable`.
- Creating a custom record now requires `custom_records.manage` at the service level (covers add-ons and sheet import); reassigning a contact checks for a duplicate phone in the new owner's list; restoring a deleted employee checks `users.manage` scope.
- Cron schedules for add-ons are validated over a full week; the attendance export warns when it is truncated; the public login endpoint rate-limits by the proxy-aware client IP; `verify_token` and `oauth_token` query keys are redacted in logs.
- Web: POS asks before discarding an unsaved cart, kanban custom fields save per field (debounced), reminder times use local time, and several silent failures now show an error.
- Update endpoints return 400 (not 500, or a silently stored null) when a required field is sent as `null` (kanban labels and custom fields, job titles, contacts, projects, notification templates, users, employees). Clearing the phone number of a user or employee now actually clears it. Notification template and salary formula syntax is validated on save.
- Employees: editing checks for a duplicate phone, accepts only the user's own current avatar path, and lock/delete are written to the audit log. Add-on jobs stop running when the approver is locked or deleted.
